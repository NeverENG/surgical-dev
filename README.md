# 手术刀开发

用于**执行已确定方案**的 Codex skill。在现有 Git 仓库里开发功能或修复问题时，用它管住改动范围、测试和交付；方案讨论不交给它。

## 执行时做什么

| 主题 | 执行时要想清楚 | 如何落地 |
| --- | --- | --- |
| 需求契约 | 谁调用、交给谁处理、什么结果算完成？ | 开工前列出各部分职责、输入输出、异常与验收场景。有歧义就问；明确的部分直接做，用户要求确认时先等确认。 |
| 改动边界 | 为实现这条链路，需要碰哪些文件和代码段？ | 修改前记录工作区及暂存区基线；修改后用文件 SHA-256 与暂存区索引拦截越界改动。允许修改的文件仍逐段审阅差异，以当次指纹签核。新增必要文件先登记理由。 |
| 测试 | 先用什么场景证明需求成立？失败究竟出在哪里？ | 先设计正常、边界、失败和回归场景，再让测试与最小实现按小步迭代推进。失败先查实现、环境和契约；确认测试自身有错才改测试。 |
| 最小链路 | 能否不碰基础架构就让一个真实流程跑通？ | 先接通入口到结果的最短路径，再补边界。必须改基础架构时，说明影响并等用户决定。 |
| 代码职责 | 客户端调用、元数据和业务判断是否混在一起？ | 沿用已有分层，按职责拆开，做满足契约的最小实现；不夹带重命名、格式化或无关重构。 |
| 文档事实 | 行为变了，哪里能查到现在的架构和功能？ | 仅对已有相关文档做最小同步；开发过程留在 Git，CHANGELOG 只做索引。 |
| 用户体验 | 用户如何知道操作成功、失败以及下一步怎么办？ | 交付前检查入口、反馈、错误提示和恢复路径；后端任务检查调用方看到的行为。 |

闸门能自动发现越界**文件**，不能靠哈希判断同一文件中某段改动是否无关；逐段审阅是签核的一部分。无关改动不交付。

## 使用

安装到 Codex 的 skills 目录：

```sh
git clone https://github.com/NeverENG/surgical-dev.git ~/.codex/skills/surgical-dev
```

在仓库任务中直接调用，例如：

```text
$surgical-dev 在这个仓库修复“保存配置后没有结果提示”。沿用现有架构；成功时给出确认，失败时说明原因，原有读取行为不能退化。先列验收场景和职责，有歧义再问我。
```

skill 会在修改前建立基线，结束时运行测试、展示差异并执行范围签核。需要自行核验时，闸门脚本位于 `scripts/scope_gate.py`，提供 `start`、`extend`、`check` 三个命令。
