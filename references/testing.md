# 测试设计：按变更风险选场景

先用一句话写明：**什么错误改动应该让这条测试失败**。从现有文档和本次契约独立得出预期；不要调用被测实现来计算期望值，也不要只断言 mock 被调用、文件包含某段文字或私有结构未变化。测试名写可观察行为，一条测试尽量只核对一个行为。

## 场景清单

从实际改动涉及的格子中选取，不为凑覆盖率把所有格子都写一遍。每个场景写清初始状态、触发动作、可观察的结果/副作用。

| 场景 | 什么时候要测 | 例子 |
| --- | --- | --- |
| 主路径 | 每个新行为 | 用户保存有效配置后，重新读取能得到新值且收到成功反馈。 |
| 边界与空值 | 可能改变分支或格式时 | 空输入、最小/最大值、缺字段、重复提交。 |
| 失败与恢复 | 有校验、网络、存储或权限失败时 | 保存失败不伪称成功，不丢失原数据，调用方得到可恢复的错误。 |
| 回归与兼容 | 修复缺陷、修改既有接口或数据时 | 原问题可复现并被测试捕获；旧调用方式或已有数据继续按契约工作。 |
| 组件接缝 | 跨客户端、领域、元数据或存储边界时 | 输入输出格式一致，错误由负责的一层处理，没有串层副作用。 |
| 状态与并发 | 有持久化、重试、异步或并发时 | 状态转换、重试上限、重复请求、乱序结果；只覆盖确实存在的行为。 |
| 用户体验 | 有可见界面或调用方反馈时 | 真实入口可操作，成功/失败反馈可见，失败后能继续或重试。 |

## 选测试层次

- **一条最小真实链路**：跨层变更先证明入口到结果能跑通；网页任务可用实际渲染与交互核验，API/CLI 任务核验真实调用结果。不要把所有层都 mock 掉。
- **聚焦的单元测试**：对独立规则、边界和失败分支写快速测试。跨层契约有风险时再补集成/契约测试；不是每个方法都要独立测试。
- 只在依赖慢、昂贵或外部不可控时替换该依赖；保留本次契约依赖的真实副作用。测试替身应模拟完整相关响应；断言真实输出/状态，而不只是替身调用次数。需要验证调用次数或顺序时，它们必须属于契约。

## 执行和诊断

1. 在写生产代码前设计场景。优先先运行测试，确认它因**目标行为缺失**而失败；若同一小迭代内测试与实现同步开发，也要证明测试有能力识别相关失败。旧缺陷优先保留可复现的失败案例。
2. 做最小实现，先跑针对性测试；失败时先看错误、复现步骤、最近改动和各组件边界的输入输出，确认根因，再改生产代码。只有确认测试预期/夹具错误时才修改测试，并说明原因；不删断言求绿。
3. 对本次变更的关键错误做一次反事实检查：如果去掉错误处理、走错分支或跳过副作用，至少有一条测试会失败吗？没有就补能观察该行为的测试。
4. 交付前重新运行相关测试、邻近回归测试和仓库已有的可行验证命令；如完整测试套件不可运行或有原有失败，记录命令、失败项和影响，不把局部通过说成全部通过。
